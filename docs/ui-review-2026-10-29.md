## 1. What I verified before writing this

Facts, not impressions:

- Rule modes: the UI only speaks easy mode. `easyModel.ts`, `EasyLibraryForm.tsx`, `easyControls.tsx` and nothing else. The server already stores a `flow.Target` and parses `flow.EasyModeInput`, so the data model is ahead of the UI.
- `DECISIONS.md` item 6 already requires all three tiers on one engine: easy mode, step stack, advanced visual flow, with the lower tiers generating the same format the advanced editor edits. Item B3 says the flow engine is post MVP, so this is a known deferral and not a surprise.
- Node on/off is half built and I want to be precise about it. `NodeRegistry.Authenticate` does reject a node when `!node.Enabled`, so the toggle is enforced for claiming new jobs. What is missing is the human side: the built-in node is created enabled, `svc.Start(ctx)` starts the worker loop unconditionally at boot, there is no start or stop control on the Nodes page (only an enabled checkbox inside the edit form), and there is no drain state. So today the answer to "should it run without being told" is: it does run without being told.
- Only `LibraryDetailPage` wraps its table in `overflow-x-auto`. Everything else overflows freely.

## 2. Mobile layout and the white page

### Root causes

1. The shell is a hard coded flex row with a fixed `w-56` sidebar and no breakpoints at all. On a phone the nav never collapses, so content is squeezed into 166 px.
2. Nothing paints the page background. The shell div carries `bg-slate-950`, but `html` and `body` do not, so every pixel outside the shell box is white. That is the entire "half the page is white" symptom.
3. Content widths are set per page with ad hoc `max-w-2xl` and similar, with no shared container, so pages do not agree on their layout and none of them adapt.
4. Tables are laid out for a desktop and are not converted to card rows on small screens.

### Design

Shell rewrite, three states:

- Under `md` (768 px): slim top bar with the product name, a hamburger, and a live job indicator. The nav becomes a slide over drawer. Optionally a bottom tab bar with 5 icons, which is what people actually expect on a phone.
- `md` and up: the current left rail, but width driven by a `--nav-w` variable and collapsible to icons.
- Always: a single `PageContainer` component with `mx-auto w-full max-w-7xl px-4 sm:px-6 lg:px-8` so every page shares one grid.

Specific fixes, all small:

- Add `bg-slate-950` to `html, body` in `index.css`, and `min-h-dvh` (dynamic viewport height, handles mobile browser chrome) on the shell. That alone kills the white band.
- Replace `w-56` with `w-56 md:w-56` and hidden under md.
- Sidebar links get 44 px minimum touch targets.
- Every table gets the `overflow-x-auto` wrapper, and under `sm` the file and node tables switch to stacked cards via a `hidden sm:table-cell` pattern on secondary columns.
- Test at 390 wide and 768 wide. No exceptions.

### Regression protection

Add Playwright to CI with two viewport smoke tests per page that assert no horizontal overflow and that the shell covers the viewport. The repo is public now and Actions is free, so this costs nothing, and it is the only way a layout bug like this does not come back in three weeks.

## 3. The three rule tiers

### Current state

Easy mode compiles a slider and a few checkboxes into a `flow.Target`, which is stored as `target` JSON on the library. There is no step stack and no canvas, and there is nowhere in the UI to see or edit what the slider actually produced.

### Design principle

One storage format, three editors. The `Target` struct is a good v1 but it is not a flow. The end state is a flow graph as the canonical stored object, with easy mode and step stack as generators that emit it. That is what DECISIONS item 6 already says, so the plan is to catch the UI up to the decision rather than invent one.

Schema sketch:

```
flows(id, library_id, version, graph_json, source CHECK IN ('easy','steps','advanced'), updated_at)
```

`graph_json` is nodes plus edges:

```
{ "schema": 1,
  "nodes": [{"id":"probe","type":"probe"}, {"id":"v","type":"video_transcode","params":{...}}],
  "edges": [{"from":"probe","to":"v","when":"codec != target.codec"}] }
```

The Go side owns validation and a `flow.Compile(graph)` that produces the ffmpeg command plan the worker already knows how to run. Keeping the graph authoritative in Go means a hand written API client and the UI cannot disagree.

### Tier 1, easy mode (keep, small upgrade)

- Keep the 5 step slider, the checkboxes and the folder picker exactly as they are. Nobody's first run should get harder.
- Add a "what this does" disclosure that shows the generated steps in plain language: "Probe, then if the codec is not HEVC, encode with CPU HEVC at quality 3, downmix audio to stereo AAC, keep English subtitles, replace the file if smaller."
- This is also the bridge that teaches the user the vocab for tier 2.

### Tier 2, step stack (build this first)

Ordered list of steps, each with a condition, add and remove rows, drag to reorder. This is the Tdarr and FileFlows mental model that most people actually want, and it costs a fraction of a canvas.

- Step types to ship: probe, if codec is not X, if bitrate above N, transcode video, remux container, convert audio to channel layout, keep or drop subtitles by language, rename by pattern, skip if smaller.
- Each row renders as one line with the condition in muted text and a params chip row.
- No canvas library needed. Plain list with drag handles.

### Tier 3, advanced flow (build second)

- Use `@xyflow/react` (MIT, the maintained React Flow), which gives pan, zoom, node dragging, minimap and connection handles for free. Do not write a canvas.
- Node palette on the left, inspector on the right, one node per step type from tier 2 plus branches and a manual FFmpeg node for people who want raw control.
- Validation lives in Go. The UI calls `POST /api/v1/flows/validate` and shows the returned errors on the node itself, so the client never guesses.
- Read only mode first (render the graph that easy mode generated), then editing. That gives people the mental map before they can break things.

## 4. Dashboard should be a dashboard

Today the dashboard renders an empty state with the full add library form inside it, and an "Add folder" button that duplicates the Libraries page.

## 6. Nodes: explicit start and stop

This is the most important functional change in your list, because a media encoder that starts moving files on its own is not defensible in an open source tool.

### Current behaviour, verified

- First run creates the built in node with `enabled` true.
- `svc.Start(ctx)` in `cmd/shrinkyourshit/main.go` starts the worker loop on every boot, with no gate.
- `nodeAuth` rejects a disabled node, so toggling enabled off in the edit form does stop new claims.
- But: the toggle is buried in an edit form, there is no status feedback, disabling does not touch the job already running, and nothing on screen tells you the queue has stopped moving because every node is off.

### Design

Worker state machine, per node:

```
stopped  -> starting -> running -> draining -> stopped
                             \-> error
```

- `stopped`: polls nothing, claims nothing.
- `running`: claims up to `concurrency` jobs.
- `draining`: claims nothing, finishes what it has, then goes to `stopped`.
- `error`: last transition failed, with the reason shown on the card.

Storage: add `desired_state` and `concurrency` to the nodes table. The worker already heartbeats, so the heartbeat response carries the desired state. No new port, no long poll, no webhook, and a stopped node costs one tiny request per interval.

API additions to API.md:

```
POST /api/v1/nodes/{id}/start     -> desired_state=running
POST /api/v1/nodes/{id}/stop      -> desired_state=stopped, body {drain: bool}
POST /api/v1/nodes/{id}/drain     -> desired_state=draining
PUT  /api/v1/nodes/{id}           -> concurrency, throughput, path mappings
```

UI, Tdarr style:

- One card per node. Big state pill at the top: Running, Stopped, Draining, Error, with color.
- A single primary toggle, Start or Stop, with a "finish current job first" checkbox when stopping.
- Under it: concurrency stepper, current job with percent and ETA, last heartbeat, ffmpeg version, encoders detected, throughput limit.
- A global switch in the header, "Pause all encoding", that stops every node at once. When any of this is off, the dashboard shows a banner: "Encoding paused on all nodes. 43,655 files waiting." Nobody should have to guess why nothing is happening.
- New installs default to `stopped` and the setup wizard ends with an explicit "Start the built in node now" step. Never start work on someone's library because they finished the wizard.

Safety details:

- Disabling or stopping a node must never delete a job. The job returns to the queue on heartbeat loss, which the runner already handles.
- Stopping mid job leaves the current file half encoded in scratch. That is fine, the runner already keeps the original until verification passes, but the UI should say so instead of leaving a mystery folder.

## 7. Other problems I noticed while reading the UI code

These are smaller but they are the difference between a demo and a tool people trust.

- No toasts. Every mutation is silent, so a user cannot tell the save worked. Add one small toast system and reuse it everywhere.
- No confirm dialog on destructive actions. Delete library should ask, and it should say whether files on disk are touched. Today the API deletes DB records only, which needs to be stated in the UI, not just in a doc.
- Errors are one line with no detail, for example "Cannot load the settings." Show the status code and a short reason, with the full JSON behind a disclosure.
- No global job indicator in the header. With encoding running, nothing on a Library page tells you work is happening.
- Loading states are plain text in some places and missing in others. Use skeletons for tables and cards.
- No pagination or filter controls on the file list beyond the status filter, which will hurt at the 40k file scale you actually run.
- Settings has no validation feedback before submit.
- Accessibility: keep the existing `aria-label`s, add visible focus rings, and give the dialogs proper roles and traps. Cheap now, expensive later.
- No keyboard escape from modals. `FolderPickerModal` needs it.

## Mobile pass (2026-10-30, task 22)

What task 20 measured and task 22 closed, in the shape this review asked for.

**Measured.** The task 20 audit held everywhere except one route: the flow
canvas page (`/libraries/:id/flow`) was never audited, and in a real browser
it did not render at all — a blank page, at every width. Cause: the server's
`GET /flows/step-types` marshals a step type without parameters as
`"params": null`, and `chipsFor` mapped over it. The jsdom fixture always
sent `params: []`, so unit tests never saw it. The whole app unmounted, so
the audit had nothing to measure.

**Changed.**

- `web/src/api.ts`: `getFlowStepTypes` normalizes `params: null` to `[]` at
  the source, so every consumer (`chipsFor`, `defaultParams`, palette,
  inspector) sees an array. One line at the boundary instead of a guard in
  each consumer.
- `web/src/FlowCanvasPage.tsx`: below `md` (768px, via
  `useMediaQuery('(min-width: 768px)')`) the page is view only — no palette,
  no inspector, no edit controls, no banner CTA. It renders
  `flow-mobile-notice`: "Viewing only on a phone. Editing the flow needs a
  desktop browser." The canvas stays with pan and pinch zoom and the step
  count stays visible. Editing state is `requested && wide`, so a resize
  mid-edit degrades to viewing with the unsaved guard armed.
- `web/src/index.css`: React Flow's zoom buttons default to 26px and the
  attribution link has no tap target; both are sized to the 44px minimum
  under `main` (scoped, because the canvas route is lazy and its stylesheet
  loads after `index.css` — an equal-specificity override would lose).
- `web/e2e/mobile.spec.ts`: the library id is fetched at runtime from the
  API; `/libraries/{id}` and `/libraries/{id}/flow` join the audit at 320,
  390, 414 and 768, and the flow leg proves Zoom In actually moves the
  viewport on a phone.
- Page buttons moved onto the shared `uiControls` classes (min-h-11), so the
  audit passes at every width on desktop too.

**Still open.**

- Mobile editing of the flow: deliberately out, same reasoning as before.
- The task 20 open questions stand: minimum font size and portrait tablet
  (768 to 1024, icon rail plus table) are still compromises worth a look.
